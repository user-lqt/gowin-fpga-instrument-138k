1 项目首先要回答的问题
我们不是要做一个“播放音乐文件的 FPGA 播放器”，而是要做一个由演奏动作驱动、由 FPGA 硬件逻辑逐样本生成声音的实时电子乐器。评委应能看到：按下/触摸/施压等动作先变成控制事件，事件进入 FPGA 内部的声部和振荡器，最后通过 I2S 输出到 DAC；音频不是预录的整段 PCM。
问题
本项目的答案
演奏者输入什么
音符、按键触发/释放、力度、编码器/距离/触摸等连续表情
FPGA 计算什么
音符到频率、相位累加、波表/FM/加法音色、ADSR、复音混音
如何发声
FPGA 生成采样 → C 的后端管线 → I2S → PCM5102A → 音箱
如何证明合规
RTL 可读、测试模式多频率输出、频谱可见独立峰、无整段预录音频播放
基础目标
≥2 独立演奏维度、≥4 复音、独立 ADSR、实时变调、延迟≤10 ms
冲奖方向
16/32 复音或等价振荡器、≥2 音色、≥3 维表情、至少一种硬件音效、延迟≤5 ms

5 为什么必须分成独立工程
Gowin 的 .gprj、顶层、.cst 和 .sdc 很容易被多人同时修改造成冲突；因此 A/B/C 各自拥有自己的仿真工程和目录。
A 可以用 testbench 假事件独立完成 DDS/ADSR；B 可以用波形激励独立完成输入；C 可以用固定正弦样本和 stub 独立完成 I2S/音效。
只有在“独立验收通过”后才合并；合并失败不能反过来阻塞成员继续开发。
最终工程不是三个人同时编辑的共享文件，而是 C 在系统分支上按版本合并的集成结果。

6 冻结的接口：三个人靠什么协作
B → A：event_valid, event_type, note_id[6:0], velocity[7:0], param_valid, param_id[3:0], param_value[15:0]
A → C：audio_core_valid, audio_left/right signed[23:0], active_voice_count[5:0], engine_ready, overload_flag
B → C：ui_page[3:0], ui_param_value[15:0], key_state[15:0], sensor_state, input_ready, ui_dirty
C → B：system_ready, audio_locked, i2s_active, system_error
EVENT_NOTE_ON、EVENT_NOTE_OFF、EVENT_PARAM_CHANGE 的编码在阶段 0 冻结。
所有模块明确 clk、rst_n、sample_tick、valid 脉冲宽度和复位值。
接口只传语义，不传对方内部实现：A 不知道事件来自哪个传感器，C 不知道 A 如何生成波形。
接口变更必须增加版本号并同步更新两个相关 testbench。
7 开发方法：先独立证明，再逐层合并
模块级仿真：每个人用自己的 testbench 证明内部逻辑，先不接真实硬件。
模块级综合：A/B/C 分别检查 RTL 能否综合；A 看音频资源，B 看状态机，C 看 I2S/效果资源。
接口级仿真：C 用 stub 或真实模块检查边界握手、时钟和状态传递。
板级最小链路：C 先用固定样本让 DAC 发声，再接 A 的真实采样。
系统级基础版本：接入 B 的键盘和参数，完成 4 复音和第二演奏维度。
冲奖扩展：在阶段 2 标签上分支扩展，任何新增功能先独立验证，避免破坏可提交版本。

后续升级目标为64复音：本轮仍以32复音成品验收为准，音频架构按可配置声部数规划。32复音稳定后，A扩展声部调度与混音，C协调至少7位声部计数接口及资源、时序、采样预算验证，B同步显示；64声部实际同时输出并通过最大负载测试后才标记完成。
阶段三最终验收回归四声部、32声部、NOTE_OFF、复位、混音饱和和I2S稳定性；C记录资源、最坏采样运算时间与延迟。高负载失败时先简化音色运算或效果，不覆盖阶段2基线。

时间分配建议：共同冻结占剩余时间10%，阶段3实体琴键/EC11_A/音色与系统集成占50%，阶段4 EC11_B、传感器表情、滑音/弯音/颤音、LED和成品装配占25%，最后15%只做回归和演示冻结。实际截止日期由团队填写，不假定还有固定天数；MCP3008、摇杆和FSR到货后统一进入阶段4。
优先削减蓝牙/App、附加混响/合唱、复杂频谱界面和外观装饰；阶段三必须保住电钢琴、另外两种音色、32复音、真实输入和稳定发声。三音色、32复音、三维表情、≤5ms及LED指引若未通过，必须在最终启用功能表中如实标记，不能以保底版本冒充全部拓展完成。
12A 阶段三四执行细则

本节是总计划书对阶段三、四的具体化版本。它规定“谁改什么、怎么证明、什么不能算完成”，个人任务书可以补充实现细节，但不能降低这里的阶段门槛。

### 12A.1 阶段三唯一交付目标

阶段三不设置16声部、两种音色或“首次可演奏”的对外中间节点。模块可以先局部仿真，但团队验收只有一个结果，必须同时满足：

| 类别 | 阶段三必须完成 | 不纳入阶段三 |
|---|---|---|
| 实体输入 | 24键亚克力琴键、48个双触点、矩阵扫描、力度、至少四键和弦 | MCP3008、FSR、摇杆 |
| 面板控制 | EC11_A调总音量，EC11_A短按循环三种音色 | EC11_B的有效功能 |
| 音频 | 32个独立声部、三种可辨音色、ADSR、混音、声部抢占、NOTE_OFF | 滑音、弯音、颤音 |
| 系统 | A/B/C完整接入、I2S/DAC、屏幕基本状态、基础音效旁路、复位恢复 | 阶段四传感器三维表情 |
| 证据 | RTL、testbench、波形、综合时序、上板发声和基础延迟 | 未实测的拓展指标不能写成完成 |

### 12A.3 阶段三集成顺序

1. C用固定正弦或已验证A2样本回归I2S、复位和DAC。
2. A提交32声部和三音色的独立仿真；C用标准事件接入，不等待实体琴键。
3. B完成24键单键样机和EC11_A仿真；先检查同帧A/B触点，再接入实体键床。
4. C接入24键NOTE_ON/OFF、velocity和EC11_A的PARAM_VOLUME/PARAM_INSTRUMENT。
5. C完成音效旁路、RGB屏基本状态、最大负载时序和基础延迟测量。
6. 三人共同执行阶段三唯一验收；通过后才冻结stage3-award。

### 12A.5 阶段四扩展目标

阶段四不是阶段三的补交版本，而是建立在stage3-award之上的扩展阶段：

- B安装并验证EC11_B，明确一个主控制用途，避免多层菜单影响现场演示。
- C完成MCP3008 3.3V供电、SPI、通道切换、去耦、共地和管脚验证。
- B完成FSR零点/满量程标定和摇杆中心/死区标定。
- A实现单音连奏滑音、摇杆弯音和FSR颤音，并与32声部回归。
- B/C完成传感器参数滤波、变化阈值和事件限频，避免噪声造成参数洪泛。
- C完成LED脱机曲谱、最终线束、电气安全、冷启动、复位、连续运行和最终bitstream。

### 12A.6 失败时的明确降级顺序

阶段三不能通过时，先保住stage2-baseline，再按以下顺序定位和降级：供电/时钟/复位 → 管脚/I2S → 事件握手 → 32声部吞吐 → 音色复杂度 → 附加音效。三种音色和32复音是阶段三目标，不能用减少到两种音色或16声部来宣称阶段三完成。阶段四传感器尚未到货不应反过来阻塞阶段三。

15 完成定义

24 失败时的判断顺序
先确认供电、复位、时钟、管脚，再怀疑算法。
先用固定样本验证 C 的 I2S，再接 A；先用 testbench 验证 B 事件，再接真实传感器。
先减功能保住 stage2-baseline，再优化资源或恢复冲奖功能。
把“听起来不对”转化为波形、频率、频谱、延迟或状态信号问题。
25 局部任务与团队验收的关系
个人任务书中的验收是局部完成条件；本总计划书中的验收卡是团队放行条件。例如 A 完成 8 复音并不等于阶段 2 通过，还必须有 B 的稳定输入、C 的 I2S 输出和≤10 ms 延迟实测。只有局部任务和系统验收同时通过，才能进入下一阶段。
26 最终完成定义
项目完成必须同时满足：A 能由标准事件逐样本生成声音；B 能稳定产生事件、参数并提供可用界面；C 能把采样可靠送到 DAC 并完成平台、音效、约束和整机验证；基础指标有实测证据；至少一个冲奖方向可演示；冻结版本可从零复现。
